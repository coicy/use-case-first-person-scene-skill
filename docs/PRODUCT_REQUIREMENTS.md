# 产品需求基线 — 用例驱动的新软件场景概念设计器

- 决策编号：PRODUCT-002
- 状态：**已确认 / 具有产品约束力**
- 决策日期：2026-10-22
- 适用版本：v0.7 及后续版本；本文件不表示对应功能已实现
- 决策权威：用户对产品功能的明确裁决优先于历史 PRD、Prompt、基准与 Agent 自行推断
- 对应实施计划：[V07_WORK_PLAN.md](V07_WORK_PLAN.md)

## 1. 产品定义

产品名称：**Use-Case Driven Software Concept Designer（用例驱动的软件场景概念设计器）**。

该技能面向**尚未开发、尚未定型或正在设计的新软件/新游戏**。用户输入产品构想、自由文本提示词、功能需求和使用用例，由 AI **设计**并输出指定用例下的软件内部可见场景图。目标不是复刻一款已经存在的软件的截图，也不是证明软件已实现。

核心价值：
- 把抽象需求转换为可供产品、开发、设计、测试讨论的具体界面/游戏内场景。
- 主动提出符合用例目标的界面、组件、信息布局、交互反馈和视觉表达。
- 对多用例建立同一产品的设计连续性，支持探索、选定、修改与迭代。
- 对最终图像关联输入需求、设计决策和当前用例步骤，支持审核。

## 2. 非歧义性的画面边界（沿用 PRODUCT-001）

- 输出仅包含**目标软件内部可见内容**：桌面软件直接显示应用界面；游戏直接显示游戏渲染画面和必要 HUD；移动软件直接显示 App 界面。
- 默认不得出现现实中的使用者、人体、手持设备、手机机身、显示器、外部桌面、键盘、办公场景或营销样机；除非这些对象本身属于新软件/游戏内被设计的虚拟画面。
- “用户第一视角”指**用户使用目标软件时所见的内部画面**，不强制所有游戏采用游戏角色眼睛视角。游戏镜头应由新产品的设计需求决定。
- 一张图对应一个明确用例状态或步骤。分镜组是多张单帧画面的集合，不把说明海报当作单帧场景。

## 3. 设计权威与推断规则

输入信息按以下层级处理：
1. **用户明确确认/冻结的产品要求和设计决策**：强约束，禁止擅自改动。
2. **用户提供但尚未确认的素材与需求**：可作为参考，但必须保留是否确定的状态。
3. **AI 提出的设计方案**：允许积极补齐设计细节，必须标记为 proposal，并能单独修改、比较与撤销。
4. **知名软件/游戏和公开截图**：可用于学习设计模式、布局和交互，不要求精确重现，也不能未经指示当作新产品的实际界面。

区分“设计细节缺失”和“关键产品约束互相矛盾”：
- 细节缺失（如按钮排布、信息密度、视觉样式）：AI 应当提出合理默认方案，不应因为没有真实截图而阻止生成。
- 关键约束冲突（如用例主动作与已冻结导航设计矛盾）：在计划中标记 conflict，不要静默改写已确认规则。
- AI 设计提案不是既有事实；不能将“建议采用侧边栏”回写成“用户已确认采用侧边栏”。

## 4. 目标用户与触发方式

典型用户：独立软件开发者、游戏开发者、交互设计师、产品设计师和拥有用例说明的工程 Agent。

应当能从以下材料开始：
- 一句话产品构想 + 一个用例；
- 自由语言功能描述 + 一系列操作步骤；
- PRD / User Story / 验收条件；
- 已有产品设计规范、风格图或之前生成的场景（可选）。

不需要用户先创建完整设计系统、提供真实软件运行截图、手工指定每个按钮位置，或先实现软件。

## 5. 功能性需求（优先级）

| ID | 级别 | 功能 | 行为 |
| --- | --- | --- | --- |
| FR-01 | P0 | 新产品 Brief 输入 | 从提示词提取产品目标、类型、用户任务、用例步骤、硬性约束与未定设计项 |
| FR-02 | P0 | 用例驱动设计 | 先生成交互/界面方案，再生成图片提示词；明确用例动作、可见状态、信息层次和操作反馈 |
| FR-03 | P0 | 可控自主创作 | 无规定的 UI、布局和视觉风格可由 AI 设计；每个关键创作决策标记 proposed/approved/rejected |
| FR-04 | P0 | 全画幅软件内场景 | 软件/游戏内部画面；不生成现实中的用户与硬件 |
| FR-05 | P0 | 输出可追溯 | 每张场景记录来源用例、硬性要求、所采用的设计提案、状态与生图参数 |
| FR-06 | P1 | 多候选探索 | 同一用例可提出多个布局/表现方案，包含可解释的取舍 |
| FR-07 | P1 | 产品级一致性 | 统一导航、UI 组件、图标、风格、布局锚点和游戏镜头，支持跨用例复用 |
| FR-08 | P1 | 设计冻结和变更 | 用户可采纳/驳回方案并冻结决策；已冻结设计变更必须明确授权并记录修订 |
| FR-09 | P1 | 多步骤场景组 | 同用例多个状态、异常流与完成态可按选择的设计规范继续生成 |
| FR-10 | P1 | 多维质量审核 | 检查需求覆盖、交互可理解性、信息层次、场景一致性及非目标对象 |

| FR-12 | P2 | 设计变更增量生成 | 设计变更时定位受影响用例和图片，必要时重新生成并维护版本追踪 |

## 6. 建议的中间模型

建立三层 IR，避免“读需求后直接丢给图像模型”：
- **ProductBrief**：产品类型、体验目标、需求事实、约束、可选参考。
- **DesignSystem / DesignDecision**：视觉语言、导航、交互组件、页面布局、方案版本、决策来源、状态（proposed/approved/rejected）、冻结范围。
- **UseCaseScene**：用例步骤、当前操作、可见反馈、信息层次、场景构图、允许的原创内容、强制出现内容、关联设计决策。

输出需同时保留结构化模型和图像/提示词，以便后续复查与局部变更。

## 7. 生成模式

- **Explore（探索）**：面对未确定的交互/界面方案，生成至少两种可比较的设计选择；明确各自的取舍。
- **Draft（草案）**：以现有约束快速产出一个完整、可讨论的场景方案；AI 可自主补齐未定细节。
- **Consistent（沿用）**：使用已经批准/冻结的产品设计规范，生成另一个用例状态。
- **Revise（定向修改）**：只针对用户指出的设计问题修订，保留未被允许改变的设计决策。

这些为目标能力，v0.6 CLI 尚未实现这些命令或模式。

## 8. 质量与非功能约束

- 不要求新软件具备可运行实例。生成图必须明确为**设计概念图**，不能冒充真实产品截图。
- 用户明确要求的 UI 文案、数值、业务规则需要可验证；纯图像生成难保证逐字准确，必要时用程序化文字/布局合成。
- 不跨用例凭空改变先前已批准的设计决定。
- 保持模块可测试、提示词有版本/哈希、输出能定位到用例 ID 和设计版本。
- 不自动调用付费生图 API，避免密钥泄露；测试/CI 的模拟调用不等于真实视觉效果。
- 软件设计的合法创新不应被“与知名软件界面不同”这一条否定。

## 9. 非目标

- 不是还原 Godot、Blender、VS Code 等现有产品截图的工具。
- 不是自动实现可运行软件/游戏、证明代码正确性或生成 UML 的工具。
- 不是把软件贴到现实显示器/手机上的营销样机工具。
- 不是仅靠美术风格、缺少用例交互语义的普通图像提示词包装器。
- 精准现有软件截图复刻/运行截图采集可作为可选参考辅助能力，不作为 v0.7 的基础依赖或默认主流程。

## 10. 验收用例与判定

必须至少覆盖两种**原创目标产品**，不得以完全模仿已有软件代替：
- **原创桌面应用**：例如新的任务/资产管理应用。三张同产品画面：列表筛选 → 详情编辑 → 保存/错误反馈。
- **原创游戏**：例如原创建造经营游戏。三张同产品画面：选择建筑 → 查看生产/资源 → 分配工人并得到反馈。

每个产品须有一个 DesignSystem，每张图必须包含可回溯的用例 ID、明确已知约束与设计提案，并保留状态差异。至少一个用例需要展示两种设计候选，选定后重新生成另一个步骤以验证连续性。

硬性验收：全部输出仅包含软件内部内容；用户确认的必须项与冻结约束无遗漏；任何仅有结构化提示词和模拟 API 的测试不得声称完成视觉验收。实际图像的可读性、设计合理性与一致性由人工逐图核对并记录意见。

## 11. 历史规则继承与废止

- **继承**：PRODUCT-001 的软件内画面边界、用例 ID/来源追溯、图片哈希、人工验收、付费调用显式授权。
- **替换**：v0.6 中“缺少来源证据即禁止任何 UI 设计补充”“优先复刻真实软件截图”“原创控件均属幻想”等旧约束不再适用于新产品概念设计。
- **保留作为兼容**：六款知名软件案例可继续作为现有 CLI 的历史回归集，但不作为判断原创设计成败的主验收集。
- **代码状态**：截至本决策，只完成需求冻结与工作计划；新三层模型、设计探索与冻结机制需开发实现。
