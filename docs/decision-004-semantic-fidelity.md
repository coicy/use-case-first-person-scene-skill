# PRODUCT-004 — 软件用例概念图的真实性与语义保真（2026-10-24）

**状态：用户正式确认；优先级：P0 / 不可用视觉风格分数抵消。**
**约束对象：** 所有 Agent 生图、CLI 图片 API、手绘/程序化合成、单张界面、分镜、对照、多个场景组合、人工或自动重试。

## 决策正文

> 无论采用何种图片组织形式，最终可见内容都不得偏离目标软件的布局、结构、功能与当前用例状态。

这里的“真实软件”指**产品定义下可成立、可实现、可供用户真实使用的软件界面及内部场景**，并不要求目标新软件已经存在，更不要求它复制已有产品截图。
设计尚未确定的部分可以由 Agent 创建**明确标注的候选提案**；已经由用户指定、采纳或冻结的事实不能被擅自改变。

## 五条语义保真不变量

1. **产品身份**：画面实际属于输入的产品类型、业务领域和场景，而非其他项目的缓存界面或串场内容。
2. **布局拓扑**：导航、主工作区、情境面板、视口、固定 HUD 等区域的相对位置、层级、职责与已选设计规范一致。样式可变，但不能偷偷改换已确定的布局结构。
3. **组件与信息结构**：可见对象、控件、标签、数据、父子关系、选中关系与目标用例一致。不存在凭视觉装饰而生成的无意义重复控件、无法解释的栏目或不属于该软件的对象。
4. **功能与交互**：控件提供的操作、可执行条件、信息输入与反馈能够解释当前用例；不得显示业务上不存在的能力、互相矛盾的功能关系、错误的权限或动作结果。
5. **状态与连续性**：显示的数据、选中对象、成功/失败、启用/禁用、跨步骤延续对象均保持合理。只有用例动作或明确允许的设计修订才能引起相应变化。

**硬失败：** 目标产品错误；违背用户或已冻结设计规则；关键功能未出现或错误；操作状态矛盾；对象/组件关系无法支撑指定用例。
**必须澄清或复核：** 产品规格不足、无法仅凭像素证明实际功能、关键文字不清晰或某些未知数值可能为模型假设。
**不是自动失败：** 合理的原创布局；风格变化；用户明确需要的分镜、拼图、比较板；界面内部合法的多面板、弹窗或分栏。

## 图片组织形式与内容语义分离

- **图片内容**必须始终满足本决策，与组织形式无关。
- **交付格式**单独服从当前任务：请求单个用例时不能用六宫格代替；请求多步骤分镜/对照图时可以展示多个画面，但每一面板都必须逐项满足所展示步骤的事实约束。
- 多画面作品应具有可核验的 panel → product / use_case / step / design_revision 对应关系；不得不同产品内容串场，除非用户明确要求对比不同产品。
- 任何拼贴、裁剪或事后重排都不能修补内部已错误的控件、对象、业务逻辑与状态。
- “单帧构图通过”或“视觉优美”不是“用例正确”的证明。

## 源事实优先级和新产品创新空间

1. 用户明确产品需求、用例状态与硬性禁止项。
2. 用户选定、批准或冻结的 DesignSystem 与结构化设计决策。
3. 从以上事实演绎出的布局、对象结构与操作状态约束。
4. 尚未确认的 Agent 原创提案，应显式保留 proposed 身份，不能静默变为软件事实。
5. 真实已有软件案例仅作为设计可行性参考，不能把它们的 UI 当作新产品必须复刻的目标。

没有锁定的布局仍应符合类别常识、软件工程可实现性及用户操作目标；一经选定，后续图像必须沿用该设计，除非用户明确修订。

## 验收矩阵：每个画面/面板独立判定

| 轴 | 关键问题 | 硬失败例子 |
|---|---|---|
| Identity | 这是目标产品吗？ | 建造游戏画成素材管理器 |
| Layout | 区域定位和导航是否与 DesignSystem 一致？ | 固定右侧 Inspector 变成无关全屏商城 |
| Structure | 控件、对象和关系是否成立？ | 列表选中 A，详情显示 B |
| Functionality | 控件是否对应用例动作及合法结果？ | 保存失败步骤显示“已成功保存” |
| State | 数值、选择和跨步骤变化是否有因果？ | 分配工人后人数减少且无解释 |
| Evidence | 关键可见元素是否完整？ | 筛选条件或筛选结果缺失 |
| Presentation | 是否采用本次要求的组织形式？ | 仅请求单界面却返回六宫格 |

每项评审结果可为 `pass` / `fail` / `uncertain` / `not_applicable`，记录观察到的证据、关联的需求/设计 ID、图片区域和评审来源。**任一硬性语义轴失败即内容不通过**；不可由外观质量、单帧通过、模型自评的总分或格式正确抵消。关键轴不确定时，只能等待复核，不能自动认定通过。

## 工程责任与状态

- **规划/生成前**：建立软件事实合同（ProductBrief + DesignSystem/Decision + Scene State）；没有冻结的内容允许生成拟议方案，但必须保持合理性与内部自洽。
- **生成时**：一个任务只携带对应产品和场景的事实合同；多面板输出必须携带逐面板约束，不能仅凭装饰性展示词指导生成。
- **生成后**：优先检查 Identity / Layout / Structure / Functionality / State，再检查呈现格式和美术效果；逐图记录依据。
- **不合格重试**：修复具体的对象、布局或功能错误，保留未被允许修改的设计决定。多画面裁剪不是自动修复语义错误。
- **实际实现状态**：截至本决策，现有 `concept-audit` 已检查构图/产品匹配/可见证据，但尚未提供独立的上述五个保真字段的完整自动化证据与真实视觉准确率。须作为 WP-05 的新增质量门禁实施，不得宣称已实现。

## 旧规则如何迁移

- PRODUCT-001（只绘制软件内部画面）、PRODUCT-002（新软件设计，允许原创提案）、PRODUCT-003（优先 Agent 原生生图）继续有效。
- 旧文档中“只有单帧才是好图”的口径只适用于**任务明确要求单场景输出时的格式约束**，不应当升级成不允许任何分镜/对照图片的普遍质量定律。
- 历史六宫格测试不能只按“是否拼贴”评级，应另行标注每个子画面是否属于目标产品，界面/功能是否真实；仍然不能作为六张独立生成成功图片。
