# v0.7 工作计划 — 新软件用例概念设计

- 状态：**已制定，待逐项实施**
- 依据：[PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md) — PRODUCT-002
- 原则：先建模、后设计、再生图；不再围绕现有软件截图复刻构建主流程
- 当前运行版本：v0.6.x；本文不是已经完成的功能清单

## A. 工作包与交付门槛

### WP-01 — 契约、输入和模型（P0）

任务：
1. 新增 ProductBrief schema：产品类型、目标用户、体验目标、功能要求、用例和不确定项。
2. 增加 DesignDecision schema：决策 ID、proposal 内容、取舍、依据、状态、关联用例和版本；禁止静默改变 approved/locked 规则。
3. 增加 SceneDesign schema：一个具体用例步骤的用户目标、画面信息层级、交互对象、状态变化、布局和视觉规范。
4. 建立迁移桥：当前 v0.6 结构化 use case 可适配新模型；标记为 historical 或 explicit requirement，不伪造用户批准。
5. 添加严格 schema + 行为回归测试（合法原创建议、非法更改硬性要求、缺少真实截图仍可规划）。

交付：三个 JSON Schema、可复现模型示例、验证/迁移代码和离线测试。

退出条件：只给一句产品构想和一个用例，也能生成有 proposed 标记的合法设计模型；遇到产品约束冲突必须出具冲突信息。

### WP-02 — 用例驱动设计引擎（P0）

任务：
1. 开发 design-plan，将需求事实分离为 MUST / MAY / UNKNOWN。
2. 先设计信息架构、核心控件与可见交互反馈，再编译图像提示词。
3. 对用户未规定的布局、颜色、组件风格、图标等提供合理默认建议。
4. 支持一个用例生成两到三个设计候选，并列出取舍和状态。
5. 防止设计方案偷偷覆盖硬性产品要求。

交付：ProductBrief → DesignDecision → UseCaseScene 的稳定流水线；规划结果、决策表、渲染提示词。

退出条件：同一输入可复现决策标识和模型；替换设计方案不改变用户硬性用例事实；无截图也可规划。

### WP-03 — 视觉规范与跨用例连续性（P1）

任务：
1. 增加 product-level DesignSystem：布局栅格、导航、通用组件、字体层级、色彩、游戏镜头等。
2. 提供 proposal → approved/locked 的显式决策状态和修订记录；未经授权不得自动冻结。
3. 生成后续步骤时，继承前述已经选定的页面/游戏设计元素和状态。
4. 对冲突、变更影响、缺失依赖输出结构化报告。

交付：设计基线、锁定/修订机制、同产品多步场景计划与差异报告。

退出条件：第二/第三个用例不无故更换布局；试图改动冻结决策被拒绝或要求显式批准。

### WP-04 — 生图编排与视觉验收（P1）

任务：
1. 调用现有生图适配器，增加 explore、draft、consistent、revise 四种目的性编排。
2. 在允许的情况下保留既有截图/参考图作为风格资料，但不要求其成为像素真值。
3. 将 image hash、scene ID、选中方案 ID、DesignSystem 版本、实际 prompt hash 绑定在交付 manifest。
4. 对照完整用例评分：操作可识别、信息可读、方案合理、整体一致与创新价值。
5. 引导用户在已有验收画廊中明确采用/拒绝候选方案；不由模型伪造人工验收。

交付：可检查的 PNG 场景组、候选方案对比、真实来源报告、人工验收记录。

退出条件：真实调用至少对两类原创产品各完成三步场景；运行测试之外有人工作出逐图判定；付费接口失败也有清楚的离线降级。

### WP-05 — 正式基准与回归（P1）

任务：
1. 新建 benchmarks/new-products：原创桌面软件 + 原创建造经营游戏的设计 Brief、用例和硬性约束。
2. 分别设计三步成功/异常/状态变化；至少一个步骤比较两个候选。
3. 加入设计决策版本、硬性约束不可丢失、生成画面边界和历史 CLI 兼容测试。
4. 继续保留 famous-projects 作为历史参考/兼容测试，不将“偏离真实软件”当成原创设计缺陷。
5. 在 CI 中只运行无付费测试；真实生图验收单独手动执行并标记费用。

交付：基准夹具、回归测试、CI、可复现的验收报告模板。

退出条件：新软件场景在需求/设计逻辑上通过自动校验，真实视觉成品得到用户逐张验收。

## B. 实施顺序

1. **WP-01**：冻结新 IR 和输入合同；这是后续所有模块的共同依据。
2. **WP-02**：打通文字需求到设计提案的流程；不在这一步优化图片细节。
3. **WP-03**：建立批准/锁定机制；让跨用例的设计保持一致。
4. **WP-04**：接入真实生图，支持多方案探索及受约束修改。
5. **WP-05**：完成原创软件/游戏基准、回归测试和视觉人工验收。

WP-05 的测试夹具可以在 WP-01 同步准备，但正式评分必须在 WP-04 真实出图之后执行。

## D. MVP 验收清单

- [ ] 从缺少真实截图的原创产品提示词生成 ProductBrief。
- [ ] AI 为需求未规定的界面结构提出至少两种可比较候选。
- [ ] 核心已知需求与 AI proposal 可清楚区分。
- [ ] 每个场景都有明确用例步骤、当前状态和可见交互反馈。
- [ ] 锁定一个 DesignSystem 后另一个步骤沿用其导航、布局和视觉语言。
- [ ] 更改已冻结决策前必须显式获得用户许可。
- [ ] 原创桌面软件 3 张真实场景图可供验收。
- [ ] 原创建造游戏 3 张真实场景图可供验收。
- [ ] 全部场景只包含软件/游戏内部内容。
- [ ] 场景图具有可追溯设计版本、需求/决策 ID 和真实生成来源。
- [ ] 人工逐图判定需求符合度、可理解性、可读性、一致性与设计价值。
- [ ] 旧 CLI 兼容测试及 Python 3.10/3.12 CI 继续通过。

## E. 风险与处理

- **设计幻觉**：允许提出 UI 方案，但必须标为 proposed；不能重写 confirmed 需求。
- **过早冻结**：仅用户明确采纳才能 approved/locked，生成图片不代表自动批准。
- **文字画错**：关键数值、标签走确定性 UI 层/文本合成，不能宣称图像模型绝对正确。
- **多图漂移**：DesignSystem + 组件布局锚点 + 设计版本进行约束，人工审核视觉连续性。
- **模式混淆**：原创产品设计模式默认启用；现有软件忠实还原只能作为明确选择的辅助模式。
- **评测失真**：严格分开模型建议、自动校验与人工验收；只生成 JSON 或 mock 图不算完成真实生图。
- **付费与隐私**：生成调用须显式授权，API 密钥不进入文档、日志、报告。

## F. 完成定义

每个工作包必须拥有：代码、schema/接口文档、实际可运行测试、对应示例、与既有版本兼容结论和已观察到的限制。仅增加 Prompt 或 README 不能算作完成。所有合并报告必须提供 GitHub commit / Actions 链接及验收结果。
